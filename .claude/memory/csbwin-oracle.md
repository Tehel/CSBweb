`bash tools/csbwin-oracle/oracle.sh build` compiles `doc/CSBwin-src/`'s Linux build (SDL2 and GLib headers fetched with `apt-get download`, nothing installed) into `doc/CSBwin-src-oracle/`; `play <run folder> [<from>-<to>]` plays its `playfile.log` unpaced (a run in ~20 s) and prints each "Sequence/timing error" with `d.Time`, and every draw in the hex range with its callers (`draws.txt`, `c++filt`). `--version=11.014` after the command does the same for 11.014's source (32-bit, sdl12-compat), which plays all four 11.0xx runs to their end; it prints `at d.Time` every 0x400 ticks, so its last such line is only the bucket play reached.

**Why:** the port's own `--trace` only shows the port's side; diffing the two draw lists per tick found an F24 drift in minutes after hours of guessing. A drift CSBWin 2023 shares at the same place is the run's version's, not the port's.

**How to apply:** for any F24 drift, or any doubt about what CSBWin draws at a moment, run the oracle before reading code. Triage in this order: draw counts per tick on both sides (`play <folder> <from>-<to>`'s `draws.txt` against `--trace=<from>-<to>`, `uniq -c` on the tick), then the first differing tick's draws side by side by caller (CSBWin's inlined helpers and the port's split functions name the same draw differently: `STRandom` is `nextMonsterUpdateTime`'s, `Try_Directions`' first draw is `ProcessTimers29to41`'s). A `TraceLine` must only print: one that calls `PossibleMove` or any game function changes CSBWin's globals and its play. Restore the build folder's `.orig` copies and relink before trusting the oracle again. Add a `TraceLine("…", …)` call (declared in `CSBCode.cpp` by the patch) to a scratch copy for state the draws don't show. A run folder needs its `graphics.dat` and `dungeon.dat` (the collection's, `../DMweb-extra/Clone,CSBwin,Movies,Data/<movie>/<run>/`, not `tools/fixtures/csbwin-runs/`, which holds logs only; copy it to the scratchpad, as its `Playfile.log` is capitalised). For a quick trace, edit the build folder's copy (`doc/CSBwin-src-11.014-oracle/<File>.cpp`), recompile that one object and relink with `oracle.sh`'s own `g++` lines (seconds, not a `build`), and put the original back after. Before suspecting a version's code, print the inputs on both sides: DMMovie42's line-783 drift was the log's `#DMRules`, not 11.014. When the draws agree but a later tick parts, trace every `MoveObject` (11.014's `Code11f52.cpp`) and every timer as `ProcessTimers` takes it, sequence included (raw bytes 10-11), on both sides from `d.Time` 0, and diff: the first line that differs is the cause, possibly a thousand ticks before the drift (DMMovie42's line 7483 was a missile's range at 0x2d0c, shifting the timer sequences). To find which group turn parts first, copy the run folder, add a `#AITraceOn` line after the log's options (CRLF lines: insert with `\r`), `play` it, and diff the `MonsterAI [0x…] LL(x,y)@t` headers of its `TRACE000.txt` (other output runs onto the same lines: `grep -o`) against `play-csbwin-log.ts --trace=0-<t>`'s; equal draw counts with a different value mean the draws come in another order inside the tick. When both sides take the same AI path from the same inputs and only a `RandomBool()` answers differently, the stream was wrong before the tick: look at the start (the seed, the read's order: Conflux's run, [[playfile-signatures]]) before any AI code. A `draws.txt` line with no caller is a draw CSBWin's backtrace could not name (a static or inlined function): it takes a `TraceLine`, not a guess. For a DSA, pair the per-command trace (state, column, word, stack depth and top) with a `setvar i=v` line in `DSADBANK::Var(i, value)` (`DSA.cpp:143`) and in the port's `DsaBank.setVar`: the first `setvar` that differs names the operation whose inputs drifted (`&PARAM@`, `&CHAR@`, `&PARTY@`, `&MON@`), which the opcode stream hides; if those inputs are game state, see [[state-drift-under-equal-draws]]. To find the first divergent turn in a busy tick, run-length encode each side's draws by kind (DSA, `executeAmpersand`/`ProcessDSATimer6`, against the rest) and compare the runs. Don't edit `oracle.sh` while a loop runs it (bash reads scripts as it goes), and don't `pkill -f` a pattern your own command line contains. See [[memmove-source-first]] for reading CSBWin itself.
